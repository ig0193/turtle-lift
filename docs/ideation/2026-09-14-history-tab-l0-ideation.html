Grounding Context

Codebase context

lib/src/ui/history_root.dart:25-34 is the whole surface today: a ListView whose only child is an unconditional EmptyState reading “No workouts yet”. There is not even a branch for “has sessions”. lib/src/data/app_database.dart holds only a Settings table — the Session / SessionExercise / SetEntry tables do not exist yet, and neither do bodyweight or gender. Everything below is therefore being designed before its data layer is poured, which is the cheapest moment to change your mind.

L0 roots are a ConsumerWidget wrapping a ListView with screenScrollPadding(context), never a Scaffold. AppScreen.root supplies a pinned large-title header and the profile avatar, and it accepts a titleWidget (app_screen.dart:74-92). Available building blocks: EmptyState, TemplateRow, DividerRow, DisclosureRow, and BodyDiagram, whose fill hook is typedef BodySegmentFill = Color Function(Set<String> subMuscleGroupIds) (body_diagram.dart:21) — a pure function from segment ids to a colour, with nothing tying it to a single session.

The rules that bind this screen

Nothing derivable is stored. performedOn is a local calendar date; loggedAt is internal and never rendered. The app bar is pinned everywhere. The tab bar shows only at L0, so no per-tab back stack is observable. And V1 forbids achievements, badges, level-ups, duration, rest timers, notifications and AI.

External context

Apple Fitness and Hevy independently ship the calendar as a secondary drill-in and a list as the primary surface — two well-known products converging. Lists beat calendars for sparse and backdated data, where a mostly-blank month grid reads as failure; calendars win only once training is dense. Boostcamp promotes any past workout into a template directly from history. On streaks, Duolingo’s guilt framing produced documented public backlash, while tolerant units (Hevy counts weeks, not days) and Gentler Streak’s explicit “streak without shame” positioning are the counter-pattern. Heatmap research supplies one warning that maps exactly onto this app: the most-repeated failure is conflating “no data” with “zero activity” — here, a rest day versus a day the app was never opened — and colour-only encoding fails colourblind users.

How the survivors were qualified

Six frames generated 46 candidates; a fresh-context verifier that never saw the generation then tried to refute every load-bearing citation against the repo. It confirmed ten claims, refuted three ideas outright, and found one real bug. Where this document overrules that verifier, it says so.

The Split — start here

Four of the six frames, working independently, arrived at the same rule for ADR 0003’s open question. That convergence is the single strongest signal in this run, so it leads.

D1

Derived lives on the tab; authored lives behind the avatar

Top pick

One mechanical rule that decides all four disputed items at once, and keeps deciding them for every item added later.

Axis
A3 — the avatar split
Confidence
92%
Complexity
Low — it is a decision, not a build
Converged from
Four frames independently (pain, leverage, inversion, cross-domain)

DescriptionAnything computed from session rows lives on the History tab: the session list, the streak, total workouts, total sets, PB counts, the calorie estimate. Anything the user typed in, which reconfigures how records are rendered, lives behind the avatar: bodyweight, gender, and the template library. No figure appears in both places. The test is one sentence — can you name this field as “computed from Session/SetEntry rows”, or as “typed in by the user and stored as-is”? Nothing is both.

Basisdirect: the storage layer already wrote this rule down for itself. lib/src/data/app_database.dart:7-14 — “Everything here is a preference, never a derived value. … What lives in this database is the opposite: facts that cannot be derived from anything, because the user simply told us (which split they are browsing; later their units, sex and bodyweight).” direct: docs/adr/0003-l0-navigation-variant-a.md:71-74 — “the split of everything else between the History tab and the avatar destination is unresolved and belongs to whoever builds those screens.” direct: docs/04-profile-tab-userflow.md:59 — gender “determines which body diagram asset set is used everywhere in the app”, which is the clearest case of an authored fact that reconfigures rendering. external: the problem-oriented medical record splits a chart into a face sheet (standing facts that change how every entry is read) and an encounter list (dated events); pilot logbooks split the same way into front matter and flight rows.

RationaleADR 0003 delegated this to taste. This is a test instead, and it happens to split the four specced Profile sections cleanly three-to-one without anyone arguing case by case. Its real value is forward-looking: the next person who adds a field does not reopen the question, because the rule already answers it — and it is the same axis the storage layer already sorts on, so a field’s home on screen and its home in the schema can never disagree.

DownsidesIt buries the sole template-authoring surface behind a 32pt disc in the header, which is genuinely poor discovery for the one thing a new user might want to do early. That cost is real and is what M7 exists to offset. It also puts bodyweight behind the avatar while the calorie prompt that needs it lives on the tab — a hop the spec already accepts, but a hop nonetheless.

Why this ranks first

It is the only item here that a named, Accepted ADR explicitly says is owed and unowned. It costs nothing to adopt, it unblocks every other decision on this screen, and it was reached independently by four frames that could not see each other’s output. The verifier cut three of the four framings as duplicates and kept this one specifically because it is the only one anchored to a quote in the code rather than to a preference.

V1

The Coverage Map

Strongest variant

The hero is not a number. It is the body, filled by how recently each region was trained — the app’s most expensive asset doing a second job.

Axis
A4 — change over time
Confidence
84%
Complexity
Medium

DescriptionReplace the stat block with a single BodyDiagram whose segments are filled by recency rather than by one session’s trained tick — deep accent for trained in the last few days, fading through muted tones toward untouched. Tapping a segment reports “Calves · last trained 24 days ago”. The session list runs underneath unchanged. Nothing is stored; the fill is a pure function of performedOn dates and primary-muscle mappings.

Basisdirect: the fill hook is already shaped for exactly this — typedef BodySegmentFill = Color Function(Set<String> subMuscleGroupIds) (lib/src/ui/body_diagram.dart:21), documented as deliberately generic so that “handing over the whole set lets both answer without the diagram knowing that exercises exist.” Verified: nothing binds it to a single session’s boolean state. direct: the no-suggestion rule this stays inside — docs/02-workout-tab-userflow.md:7, “the app does not suggest or auto-select a workout … no rotation logic.” external: three unrelated hobby domains — amateur-radio DXCC, peak-bagging, eBird life lists — converge on the same durable form for a personal record: a fixed named set of entities, each stamped with when you last got it.

RationaleThis is the one variant that could not be lifted from another fitness app, because it depends on an asset this repo already paid to build: 42 real hit-testable segments. It answers “what have I been neglecting?” — a question the user actually has — using only facts, never advice, so it stays on the correct side of the no-recommendation line. And it gives the third tab a hero that is neither a number nor a calendar, which is the space the other five variants are all fighting over.

DownsidesA recency ramp is a colour gradient, and the research is blunt that colour-only encoding fails colourblind users — so the tap-to-name affordance is not optional polish here, it is the redundant encoding that makes the ramp legible at all. It also needs a defensible ramp: the bands are descriptive, and the moment anyone picks a threshold that implies “you are overdue”, this becomes a recommendation and violates 02:7.

What it gives up

The streak. There is no obvious place for it in this composition, so V1 either pairs with M3 (streak in the pinned header) or accepts that the streak lives only behind the avatar. That pairing is the most likely real design.

V2

The Ledger with Named Silences

A plain chronological list, except that the gaps are drawn. The rest days you took are the content, not the absence of it.

Axis
A1 — the history list
Confidence
81%
Complexity
Low

DescriptionBetween two rows whose performedOn differ by more than the tolerance, render a bare labelled spacer — — 11 days —, textMuted, no icon, no colour, not tappable. Gaps inside the tolerance get no marker at all. Month labels group the runs above it, reusing the section-label idiom muscles_root.dart already ships.

Basisdirect: the tolerance the spacer encodes — docs/01-app-idea.md:239, “a Friday → Monday gap is 3 days, so a tighter 2-day rule would break the streak of anyone training weekdays-only, and of anyone running the Push/Pull/Leg split on Mon/Wed/Fri.” direct: ordering is already settled — docs/00-build-spec.md:237, “History ordered by performedOn, loggedAt as tiebreaker.” external: stratigraphy, where a core’s most-read feature is the unconformity — a gap in deposition that geologists label and date rather than close up; and the heatmap research’s central warning that conflating “no data” with “zero activity” is the most-repeated failure in this shape of display. A labelled gap is the inverse move: the gap is the datum.

RationaleA flush list erases the difference between three sessions in a week and three in a year, which is most of what a training history actually means. This teaches the 3-day tolerance rule by showing it — the user sees which gaps the app considered survivable and which it did not — at the exact moment they are looking at the evidence, with no prose, no calendar grid, and no number. It is also the cheapest variant here by a wide margin.

DownsidesIt is the most conservative direction on offer: a user who wants coverage or progress gets neither. And because performedOn is editable, a backdated session re-inserts itself mid-column and every spacer below must be recomputed — so gap rows are derived on every build and can never be memoised against a row index.

V3

The Tolerance Strip

Fourteen marks in three states. It encodes the streak, its forgiveness, and today’s standing in one row that needs no paragraph to be read.

Axis
A2 — stats and the streak
Confidence
79%
Complexity
Medium

DescriptionReplace the three-tile stat grid with a strip of the last 7–14 calendar days in three visually distinct states: filled accentStrong for trained, outlined for a rest day still inside the 3-day grace window, empty mutedSurface for outside it. The streak number and the explainer sentence sit below it as caption, not as headline.

Basisdirect: the rule the strip must encode — docs/01-app-idea.md:238, the streak is “the count of workout days in a row where the user never went more than 3 days without training”; and the sanctioned nudge at 01:253, “a ‘streak ends tomorrow’ hint on the final grace day.” external: two findings that jointly determine the encoding — colour-only encoding fails colourblind users, and conflating “no data” with “zero activity” is the most-repeated failure of this display shape. A fill/outline/empty triple separates rest-within-tolerance from lapsed by shape, where colour alone could not.

RationaleThe 3-day tolerance is the least predictable thing on this screen, and the current plan explains it with a paragraph the user will not read. A strip where the grace days are visibly different marks teaches the rule structurally: you see two outlined days and understand that a third breaks it. It also sidesteps the blank-month-grid failure that makes calendars read as failure for sparse training, while keeping the glanceability that makes people want a calendar in the first place.

DownsidesIt is a bespoke component in an app that has so far assembled itself from four reusable rows, and three-state legibility at 14 marks on a narrow phone is genuinely hard to get right. Fourteen days is also a short horizon — it says nothing to a user who trained hard for a year and stopped last month, which is precisely the user M4 is about.

V4

The Scannable Trail

No stats block at all. Instead, every row earns its own garnish, so records and muscle coverage are visible while scrolling rather than found by opening things.

Axis
A1 — the history list
Confidence
72%
Complexity
High — gated on the foundation below

DescriptionPush the derived content down into the rows instead of sitting it on top of them. Each row gains a PB pill when pbCountFor(session) >= 1, and a small muscle silhouette filled where that session’s primary muscles were trained. Scrolling becomes the stat display: a trail of records and body regions rather than a column of titles and counts.

Basisdirect: the pill already exists one screen deeper — docs/00-build-spec.md:233, “Per-session PB count — pbCountFor(session). Rendered as a pill on the hero card only when >= 1 (never ‘0 personal bests’).” direct: the trained derivation the glyph needs — docs/01-app-idea.md:102, “a sub-muscle group is trained in a session when at least one completed exercise in that session lists it among its primary muscles.” direct: the row metadata specced today carries no muscle information at all — docs/04-profile-tab-userflow.md:24 lists only date, muscles trained, exercises, sets, and the prototype renders just “6 exercises · 18 sets”.

Rationale“Which of my last fifty sessions had a record?” and “which day did I train legs?” are both currently answerable only by opening rows one at a time. Both answers are already computed. Moving them one screen earlier costs no new derivation and turns a flat scroll into something worth scrolling.

DownsidesThis is the most expensive variant and the verifier demoted it for that reason. Instantiating the app’s heaviest custom-painted widget once per row, in a list that may run to hundreds of sessions, with per-session segment computation on top, is not viable as written. It is only meeting-ready as a pre-rasterised glyph — a handful of cached silhouettes keyed by muscle-group combination — and the PB pill is impossible at all until the single-pass projection below exists, because per-row PB derivation is the O(n²) the spec explicitly forbids.

Why it still ranks

Because the cost is a design problem, not a rule conflict, and the cheaper design is known. It is also the only variant whose value grows with history length rather than staying flat.

DescriptionThe body is nothing but the list. The derived summary moves into AppScreen.root’s titleWidget as a subtitle under the large title, so it stays on screen permanently instead of scrolling away. The word “History” survives as the semantics label.

Basisdirect: verified to exist — AppScreen.root({..., Widget? titleWidget, ...}) at lib/src/ui/app_screen.dart:74-92, under the class doc at lines 37-43: “The header is pinned. V6

The Finding Aid

Borrowed from archives: state the extent of the collection, offer two or three ways in, and let the chronological list be the container list underneath.

Axis

Confidence

DescriptionOpen with a derived extent statement — “48 sessions · Mar 2026 – today · 611 sets” — then a short row of browse-by entries, each pushing a filtered list. RationaleThe spec’s own words say the progression arc is visible in exactly one place, and both existing routes to that place require the user to already know which exercise they want — via the muscle taxonomy, or mid-set. DownsidesIt adds a second structural element above a list the spec describes as list-only, and it overlaps the Muscles tab’s existing route to the same screen — two doors to one room, which needs justifying rather than assuming. The extent line is also the weakest part: it risks reading as a vanity stat grid in prose clothing.

Modifiers

Composable with any variant above. These are not competing directions; several should be adopted together.

M1

A tappable search field, pushed as an opaque route

A1

WhatA search field at the top of the list that is not editable in place — tapping it pushes a full search screen over the tab bar. Queries resolved titles, exercise names and dates.

Basisdirect: the pattern is already shipped one tab over, with its reasoning written down — muscles_root.dart:90-99: opaque “is the only kind of route that covers the floating tab bar, and a search screen with the tab bar still floating over its results would offer to leave mid-query.”

WhyThe history list is the only unbounded list in the app — Muscles is fixed at 19 rows, templates at a handful — and it is the one surface with no search. A user two years in looking for “the session where I first benched 80” has no path at all.

M2

Group same-day sessions under one date header

A1

WhatWhen two sessions share a performedOn — a quick log plus a full workout, say — render them as two rows under a single date heading rather than as two independently dated rows.

Basisdirect: docs/00-build-spec.md:52 — loggedAt is “internal only. Tiebreaker when two sessions share performedOn. Never shown.”

WhyThis is the survivable remnant of a larger idea (make the day the row unit) that the verifier correctly refuted — a day-row needs aggregate-title logic, an ambiguous tap target, and edit/delete that resolves to one of several sessions, none of which the one-line pitch accounted for. Grouping under a shared header buys the visual coherence without any of that cost.

M3

Never render a streak of zero

A2

WhatThe streak slot shows a count only while a streak exists. At zero it shows something true and non-punitive in the same slot — “Last trained: Leg day, 6 days ago”. No red, no reset language.

Basisdirect: docs/01-app-idea.md:251 — “The streak must decay against today … If the last session was 5 days ago, streakAsOf(today) returns 0 even though nothing in storage changed.” The spec already forbids “0 personal bests” on the hero pill for the same instinct. external: Duolingo’s guilt framing and its documented backlash; Gentler Streak’s entire positioning.

WhyA derived streak returns 0 for exactly the user who has been away and is opening the app to come back — the screen’s most important visitor. A zero in the hero slot tells that person their history is worthless at the moment they are least able to argue.

M4

A tenure line — a span, not a count

A2

WhatOne derived line stating how long the user has been training with the app: “Training since March — 7 months.” Derived from min(performedOn); no schema cost.

Basisreasoned: every figure currently specced for this surface is a count or a chain, and both go to zero. Tenure is a span, and a span is the only figure a user with a broken streak can still be proud of — it is monotonic by construction, so it can never become discouraging.

WhyNothing in the app currently reflects duration of practice back to the user. It is the cheapest possible answer to “am I still in this?”, and it pairs naturally with M3 as what fills the slot when the streak is gone.

M5

Absence is never painted in accentStrong

A2

WhatA standing rule: a lapsed streak, a zero streak, a long gap and the grace-day hint are all advisory — textMuted, no accent, no danger, no icon, never animated. accentStrong means “this has been worked”, so it may never mark an absence.

Basisdirect: CLAUDE.md’s palette contract — #D85A30 “means ‘active / this has been worked’ wherever it appears”, with test/theme_palette_test.dart already failing on any colour outside §12. external: cockpit alerting philosophy tiers alerts strictly by the response they require, and promoting a condition above its required response is a certification failure because it trains the operator to ignore alerts.

WhyThe palette already enforces half of this by accident — there is no colour available for “you are failing”. Writing it down converts every future streak-shame argument into a rendering rule a widget test can enforce next to the existing palette test. The verifier called this low-information because §12 already decides colour meanings; that is overruled here, because §12 decides what the colours mean and this decides what they may be pointed at, which is the thing about to be drawn.

M6

Multi-select batch delete

A1

WhatLong-press a row to enter selection mode; delete several behind one confirmation, instead of repeating swipe-confirm per row.

Basisdirect: docs/04-profile-tab-userflow.md:28 — “Confirmation dialog, then permanent removal (hard delete; no tombstone in V1).”

M7

Promote a past session into a template

Needs a spec exceptionA3

WhatA row action that opens the template editor pre-filled from that session’s exercises, reusing the same “duplicate → editable copy” mechanism predefined templates already have.

Basisexternal: Boostcamp promotes any past workout to a template directly from history — history feeding forward into planning, not just a record. direct: and this is why it is flagged — docs/04-profile-tab-userflow.md:20 states templates are “the only place templates are created or edited”, matched by 00:241, “Only place templates are authored.”

M8

“On this day” resurfacing

A4

WhatComputed on read: if today is an exact-date anniversary of a past session, one quiet line above the list — “A year ago today: Leg day” — tapping into that session.

Basisexternal: Day One and photo libraries both pair a timeline with “On This Day” resurfacing; it is the durable pattern for making an archive re-readable. direct: stays inside the no-notifications rule, matching the in-app-only precedent at 01:253.

The Foundation

One architectural decision gates what the rows above are allowed to contain. It is not a look, but deciding it after the layout would quietly rule several of these variants out.

F1 — One chronological projection, not per-row derivation

Build a single provider that walks all sessions once in performedOn order, carrying a running per-exercise best and a running streak chain, and emits per session: PB count, streakAsOf at that date, set and exercise counts, and trained segments. Rows then read from the projection instead of each doing its own lookup, and the whole screen invalidates as one unit when a session is edited or deleted.

Basis direct: the spec already mandates the algorithm without naming a surface — docs/00-build-spec.md:235, “Compute in one chronological pass with a running per-exercise best. Not O(n^2).” Confirmed verbatim, and echoed at 01:235: “Do not evaluate each session against full history independently — that is O(n²).” direct: streakAsOf is already designed as one function taking a date — 01:249, “Same function, one parameter.”

Why it decides layout Whether a history row may show a PB pill looks like a visual question and is actually an architecture question: per-row derivation is the O(n²) the spec forbids, so V4 is impossible unless this exists. Build the projection first and a whole class of row content becomes affordable; build the rows first and it is quietly ruled out. The same projection is what the still-unbuilt Session Detail and Summary screens will need for streakAsOf(session.performedOn) — the historical streak, not today’s.

Findings & Corrections

Confirmed bug — not a design idea

Updating bodyweight silently rewrites the calorie figure on every session ever logged. Bodyweight exists in exactly one place: a single optional, undated field in the one-row Settings table. The calorie formula at 00:154 is kcal = (MET × 3.5 × bodyweightKg / 200) × minutes — it takes bodyweightKg, because there is no bodyweightAtTimeKg to take. Calories are on the derived-on-read list. Put those two independently-stated facts together and the consequence is mechanical: opening any past session recomputes its calories from today’s weight. Change 78 → 84 kg and every historical figure moves, including one the user screenshotted, and including sessions logged before they had entered a weight at all.

The fix is nearly free today and a migration later: make bodyweight a small append-only dated series and have caloriesFor(session) resolve the weight in effect on session.performedOn. This does not violate the derived-values rule — that rule forbids storing what can be recomputed, and a past bodyweight cannot be recomputed from anything. The Session tables do not exist yet, so this costs a schema decision now and a migration if deferred. It also hands the avatar destination a second surface with genuine content — a weight log — instead of a settings form.

The verifier judged this “real, currently unaddressed, and arguably understated rather than overstated — it isn’t a hypothetical edge case, it’s the default behaviour of the two rules as written.”

Two reported conflicts that dissolved

Generation flagged two apparent contradictions in docs/00-build-spec.md. Verification against 01 — which wins per CLAUDE.md — dissolved both, so no conflict needs resolving:

“Set count is the headline stat” (00:88) vs. listing it third (00:232). Not a rule conflict. 01:220 reads “Set count is the headline volume proxy instead” — a stand-in for the banned kg figure, not a claim about tile order. The digest dropped “volume proxy” and the shortened phrase reads, in isolation, like a layout instruction. That is a wording defect in 00 worth a one-word fix, and it is the exact failure mode CLAUDE.md warns about when 00 is read alone.

loggedAt “never shown” (00:52) vs. tiebreaker (00:237). A misreading. Using a field as a sort key is not displaying it; no doc anywhere says the value is rendered. 01:203 matches 00:52 verbatim.
